# 测试工作台（Test Workbench）架构设计文档

> 版本：v0.1（架构草案）
> 定位：一站式测试管理平台，覆盖测试全生命周期「需求 → 计划 → 设计 → 执行 → 缺陷 → 自动化 → 报告 → 知识沉淀」，并深度集成 AI 辅助能力。

---

## 1. 产品概述

### 1.1 产品定位
面向测试团队/测试工程师的一站式测试管理工作台，将散落的 PRD、用例、缺陷、自动化脚本、知识文档统一到一个平台管理，并提供质量度量与 AI 辅助能力，让测试从「文档驱动」走向「数据驱动」。

### 1.2 目标用户
- 测试工程师（核心使用者）：用例设计、执行、缺陷提交、脚本维护
- 测试组长/主管：计划排期、质量监控、报告产出
- 开发/产品（协同者）：查看需求、缺陷处理、回归验证
- 管理者（只读）：质量看板、覆盖率、趋势

### 1.3 核心价值
1. **全链路可追溯**：需求 → 用例 → 执行 → 缺陷 双向关联，覆盖度一目了然
2. **质量数据化**：通过率、缺陷密度、覆盖率、趋势自动统计，替代人工汇总
3. **AI 提效**：从 PRD 自动生成用例、缺陷智能分析、报告自动生成、自然语言转脚本
4. **资产沉淀**：用例库、知识库、SKILL 库可复用，降低人员流动损失

### 2.3 部署架构
- **单体部署（MVP 期）**：前后端分离，后端单服务 + MySQL + Redis，一台服务器/本地 Docker Compose 即可跑通
- **微服务化（规模化后可选）**：按需拆分为 auth / project / testcase / bug / automation 等子服务，接入注册中心

## 3. 功能模块详细设计

### 3.1 需求管理（PRD 管理）
| 功能点 | 说明 |
|---|---|
| PRD 文档管理 | 富文本/Markdown 编辑、附件上传、多版本留痕、在线预览 |
| 需求条目化 | 从 PRD 中拆分为可验收的需求点（用户故事） |
| 需求属性 | 优先级(P0/P1/P2)、模块、负责人、验收标准、关联迭代 |
| 需求评审 | 评审状态、评论、评审记录 |
| 变更管理 | 变更记录、变更影响提示（关联的用例/缺陷） |
| 追踪关系 | 需求 ⇄ 用例 ⇄ 缺陷 双向关联，覆盖度统计 |

### 3.2 测试计划
| 功能点 | 说明 |
|---|---|
| 迭代/里程碑 | 创建测试计划，绑定需求范围与版本 |
| 用例分配 | 按模块/负责人分配用例到执行人 |
| 排期与进度 | 甘特/看板视图，执行进度实时统计 |
| 准入/准出标准 | 可配置（如用例执行率≥90%、致命/严重缺陷清零） |

### 3.3 测试用例管理
| 功能点 | 说明 |
|---|---|
| 用例树 | 按项目/模块/功能多级分组，拖拽调整 |
| 用例设计 | 前置条件、步骤、预期结果、优先级、用例类型、标签 |
| 用例评审 | 评审状态流转、评论 |
| 批量操作 | 批量导入导出（Excel）、批量修改、复制、复用 |
| 模板库 | 公共用例模板、跨项目复用 |
| 智能生成 | AI 根据需求点自动生成用例草稿，人工确认入库 |
| 版本控制 | 用例修改留痕，可对比历史版本 |

### 3.4 测试执行
| 功能点 | 说明 |
|---|---|
| 执行任务 | 基于计划创建执行轮次，圈选用例集 |
| 状态流转 | 未执行 → 通过 / 失败 / 阻塞 / 跳过（支持批量记录） |
| 执行证据 | 截图、日志、附件、失败原因（关联缺陷） |
| 执行历史 | 用例每次执行记录可回溯，支持重跑 |
| 与自动化集成 | 自动化执行结果自动回填为执行记录 |

### 3.5 缺陷管理（BUG 跟踪）
| 功能点 | 说明 |
|---|---|
| 缺陷生命周期 | 新建 → 待处理 → 修复中 → 待回归 → 关闭 / 重新打开 |
| 缺陷字段 | 严重程度(致命/严重/一般/轻微)、优先级、模块、版本、复现步骤、附件 |
| 缺陷看板 | 看板视图（按状态/负责人/优先级） |
| 智能分析 | AI 自动分类/标级、相似缺陷检测、自动摘要 |
| 统计 | 缺陷趋势、Top 模块、人均效率、回归率 |

### 3.6 自动化管理
| 功能点 | 说明 |
|---|---|
| UI 脚本管理 | 脚本文件/仓库管理、版本、关联用例、运行环境 |
| API/接口测试 | 接口用例管理、断言、环境变量、批量执行 |
| 脚本仓库 | 与 Git 集成，版本对比、回滚 |
| 调度执行 | 定时任务 / 手动触发，结果回传平台 |
| 报告 | 自动化执行报告、失败截图、趋势（自动化覆盖率） |
| NL2 脚本 | AI 从自然语言/用例描述生成脚本骨架 |

### 3.7 版本与环境管理
| 功能点 | 说明 |
|---|---|
| 被测版本 | 版本列表、关联需求/缺陷/用例执行 |

### 3.8 统计报表
| 功能点 | 说明 |
|---|---|
| 质量看板 | 用例执行进度、通过率、缺陷分布、需求覆盖率 |
| 趋势图 | 缺陷趋势、执行趋势（ECharts） |
| 覆盖率 | 需求覆盖、用例执行覆盖、自动化覆盖 |
| 自定义报表 | 按时间/模块/版本维度组合，导出 Excel |

### 3.9 知识库
| 功能点 | 说明 |

## 7. 核心流程设计

### 7.1 测试闭环主流程
```
创建项目 → 上传 PRD → 拆分需求点
   → 制定测试计划（绑版本/范围）
   → 设计用例（人工 / AI 辅助生成）
   → 执行用例（手动 / 自动化）
   → 失败 → 提交缺陷 → 修复 → 回归 → 关闭
   → 质量报告（自动汇总）→ 归档至知识库
```

### 7.2 缺陷生命周期
```
新建 → 待处理（指派）→ 修复中 → 待回归
   → 回归通过 → 关闭
   → 回归失败 / 重新打开
```
- 状态流转需记录操作人、时间、备注，形成时间线
- 规则：严重/致命缺陷未清零不可发布（准出条件）

### 7.3 AI 辅助链路
```
PRD/需求 → LLM 生成用例草稿 → 人工确认 → 入库
缺陷描述 → LLM 分类/标级/查重 → 推荐处理人
执行数据 → LLM 生成周报/发布报告
自然语言 → LLM 生成自动化脚本骨架 → 人工补全
```

## 8. 权限模型（RBAC）
| 角色 | 权限范围 |
|---|---|
| 项目管理员 | 项目配置、成员管理、模块全部权限 |
| 测试负责人 | 计划、用例评审、报表、缺陷处置 |
| 测试工程师 | 用例设计/执行、缺陷提交、脚本维护 |
| 开发/产品 | 查看需求/用例、处理缺陷 |
| 访客/管理层 | 只读（看板、报表） |

- 数据隔离：所有业务数据带 `project_id`，按项目空间隔离
- 权限点：模块级 + 操作级（增删改查）细粒度控制

## 9. 开发路线图

### 阶段一：MVP（1–2 个月）——核心闭环跑通
- 项目空间 + 用户权限（基础 RBAC）
- 需求管理（PRD 上传 + 需求点拆分）
- 用例管理（树形 + 导入导出 + 步骤编辑）
- 测试计划 + 执行记录
- 缺陷管理（生命周期 + 看板 + 统计）
- 基础报表（通过率、缺陷分布、覆盖率）

### 阶段二：V2（3–4 个月）——自动化 + 资产
- 自动化管理（UI/API 脚本 + 任务调度 + 报告回传）
- 版本与环境管理
- 知识库
- 报表增强（趋势图、自定义报表、导出）
- AI 辅助 V1（从 PRD 生成用例、缺陷智能分类）

### 阶段三：V3（5 个月+）——AI 深度集成 + 规模化
- SKILL 管理 + 技能编排
- AI 模型配置中心（多供应商、Prompt 模板、用量统计）
- 自然语言转自动化脚本
- 通知集成（邮件/IM）、操作日志审计
- 微服务拆分 / 性能优化

## 10. 关键决策点（待确认）

1. **技术栈**：后端用 Python FastAPI 还是 Java Spring Boot？（推荐 Python，契合你的技术栈且快）
2. **AI 能力范围**：MVP 期是否就要 AI 用例生成，还是先做纯管理闭环、AI 后置？
3. **自动化深度**：MVP 期要不要接入真实执行引擎，还是先做"脚本托管 + 手动报告"？
4. **部署形态**：本地 Docker Compose / 个人服务器 / 云端？
5. **团队规模**：单人使用还是多人协作？（决定权限与通知的复杂度）

## 11. 风险与权衡
| 风险 | 应对 |
|---|---|
| 功能过多导致 MVP 延期 | 严格按路线图砍范围，MVP 只做核心闭环 |
| 自动化引擎接入复杂 | 先做脚本托管，执行引擎后置或先接 Jenkins |
| AI 生成质量不稳定 | 生成物一律"草稿 + 人工确认"入库 |
| 数据量大后性能问题 | 前期避免全表模糊搜索，索引设计前置 |
| 单人/小团队使用过度设计 | 权限、通知按需裁剪，避免过度工程 |
